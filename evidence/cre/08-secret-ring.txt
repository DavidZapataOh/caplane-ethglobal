The production secret ring, read once per execution — and what a green simulation does not prove.

--- the ring ------------------------------------------------------------------

Five identifiers, one batch, read on the handler's first line:

  ENCLAVE_ENVELOPE_KEY      opens the sealed submission
  COMMITMENT_PEPPER         salts the index; never rotates, because rotating it invalidates
                            every commitment ever written and there is no reindex
  LEDGER_APP_ID             accounting connection, client half
  LEDGER_APP_PASSPHRASE     accounting connection, secret half
  WATCHLIST_SUBSCRIPTION    screening key, sent as a header

All five live in the vault under owner 0xd5557A1d0806323caD77bC4049ccaca0EaDAaf06, namespace main.

A batch of N costs one call against the five-per-execution quota: the SDK reserves a single
callback id and issues one host call carrying every request. Four of the five have no reader yet
and are fetched anyway, because a missing id aborts the whole handler and one upload before this
ships is cheaper than four later.

--- there is one vault, not one per target --------------------------------------

The obvious reading of two targets is two stores. It is one. Uploading the same ring to the
second target fails per-secret:

  ✗ Secret create failed: secret_id=ENCLAVE_ENVELOPE_KEY ... error=key already exists

and listing either target returns the same five. The store is keyed by owner and namespace, and
both targets share both. Staging and production are separated by workflow name, not by secrets.

That is also the concrete form of a risk worth stating plainly: any workflow deployed under this
owner reads these five. `SecretRequest` carries only an id and a namespace — no workflow identity
— and no write operation accepts a namespace other than `main`. There is no ACL documented either
way.

Note `create` does not abort the batch on a duplicate: it reports per secret and continues, so a
partial re-upload is safe.

--- what a green simulation does not prove: it never asks the vault ---------------

This is the finding, and it took four experiments to isolate.

  1. Deleted COMMITMENT_PEPPER from the vault, simulated. Unchanged, still green.
  2. Deleted ENCLAVE_ENVELOPE_KEY — the one the handler actually reads — and simulated.
     Still green, still decrypting.
  3. Exported a zeroed CAPLANE_ENVELOPE_KEY over the shell environment. Still green.
  4. Zeroed the same variable IN THE .env FILE, vault still deleted:

     ✗ workflow execution failed: invalid tag

So `cre workflow simulate` resolves secret values from the `.env` file on disk, through its own
`-e` flag, which defaults to that file. It does not read the exported environment, and it never
consults the vault at all.

Two consequences, both of which the repository was assuming otherwise:

  · An ablation against the vault proves nothing in simulation. The plan that specified one was
    wrong about what it would show, and this file records the corrected experiment instead of the
    one that was asked for.
  · "A missing identifier aborts the handler" is a statement about DEPLOYED execution. It cannot
    be exercised here, and nothing in this repository has exercised it yet.

The vault upload is therefore required for deployment and invisible to every local verification.

--- the quota is not enforced here either, and the reason is measurable -----------

`cre workflow limits export` prints the simulator's own defaults. For secrets:

  default Secrets.CallLimit = 5        identical to prod-limits.json

So `--limits ./prod-limits.json` cannot discriminate on this quota: the value it loads is the
value already in force. That is why eight secrets calls once passed cleanly with production
limits loaded — not because the file was ignored, but because it changed nothing.

For comparison, the quotas where the default DOES differ, and where an ablation would therefore
mean something:

  HTTPAction.CallLimit          default 15   prod 5
  ConfidentialHTTP.CallLimit    default 15   prod 15
  ChainRead.CallLimit           default 15   prod 15

What actually holds the batch to one call is the SDK's implementation — one callback id, one host
call — and a hygiene rule that fails the build on a second `getSecrets` anywhere in the workflow
package. Not a green simulation.

--- the rule that was enforcing something that does not exist --------------------

The repository banned an identifier that was a substring of its variable, on the belief that the
CLI could not resolve overlapping names. Measured against the real CLI in a scratch project, with
the variables exported:

  ZZ_ALPHA_ONE: [ZZ_ALPHA_ONE]           resolved
  ZZ_API_TOKEN: [ZZ_SECRET_API_TOKEN]    resolved
  ZZ_BETA_TWO:  [ZZ_VAR_BETA]            ✗ environment variable "ZZ_VAR_BETA" for secret
                                           "ZZ_BETA_TWO" not found; please export it

It names the identifier and the variable separately: a structured map lookup, not textual
substitution. No overlap validation exists anywhere in the CLI binary, and the sponsor's secrets
documentation carries no naming restriction.

So three of the five pairs here are identical on both sides, the rule's branch was deleted rather
than left passing for a reason nobody could reproduce, and the test that pinned it was replaced by
one that pins the measured behaviour.

--- two rules added, and both shown to bite --------------------------------------

  secrets-are-read-once      a second getSecrets anywhere in the workflow package
  no-secret-through-the-door a secret value on the same line as usingTheDons() or reportFromDon(

Injected, observed, reverted:

  second getSecrets   → secrets-are-read-once: 2 secrets calls in the workflow package
  secret through door → no-secret-through-the-door: workflow.ts:121
  a derived fact      → clean, which is the shape that is allowed

The second is a heuristic and is written as one: it reads a single statement, not the flow of a
variable across functions. It catches the slip, not a decided exfiltration.

--- and one rule that had gone blind ---------------------------------------------

Moving the five ids into a constant blinded `secretNamesAreRegistered`: its pattern matched only
a literal id inside a `getSecrets` call, so after the batch it matched nothing in the entire
repository and would have passed for ever. Repaired to read the constant as well, and shown to
bite by removing COMMITMENT_PEPPER from .env.example:

  secret-names-registered: caplane-workflow/workflow.ts — COMMITMENT_PEPPER is not a key in .env.example

--- rotation ---------------------------------------------------------------------

There is no windowless rotation. `update` is not documented as atomic, the behaviour of an
execution in flight is unknown, and the whole published guidance is to change the variable and run
`update` again. The pepper cannot be rotated at all: every commitment ever written derives from
it and there is no reindex.
