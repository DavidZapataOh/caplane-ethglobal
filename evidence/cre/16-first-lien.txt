--- the subscription window loses events, measured twice ------------------------------

Registering a workflow opens its log subscription forward in time, and there is a window after
registration during which events are not seen. Not delayed — not seen.

  production registered   05:38:09
  submission #1           05:39:55   1m46s later    never executed
  submission #2           05:45:47   7m38s later    executed at 05:45:50

Three seconds, once the subscription is live. The lien carries #2's submissionId, which is how the
two cases are told apart: the execution at 05:45:50 was #2 arriving instantly, not #1 arriving
late. The same shape appeared in staging, where a submission 11 seconds after registration was
never executed and one six minutes later fired within twenty seconds.

A lost submission has no symptom anywhere. No CLI error, no chain event, no log — a TEE trigger
emits none. The only trace is a `ClaimSubmitted` with no answer, and the submitter has paid gas and
permanently consumed that submission id in the inbox.

  · For a product: submissions have to be reconciled against responses. Nothing in this repository
    does that today.
  · For a deployment: register first, submit with minutes of margin.

The other half of the same finding is good news, and it closes an open question from the
deployment audit: **historical events are not replayed.** Five `ClaimSubmitted` events sit on this
inbox; production has executed exactly one. The three that predate it — one from before the
redeploy, two from the staging exercise — were never picked up and never will be. The risk that
activating production would replay an old approval and commit pool funds with nobody deciding to
does not exist.


--- what this establishes, and what it does not ---------------------------------------

Established, and none of it had been before today:

  · The Vault DON releases five secrets into an attested enclave. Every green run before the
    staging pre-flight read them from a file on disk.
  · Four live calls to two third-party services execute from inside the enclave.
  · A report signed by the DON reaches the production forwarder and is accepted by a contract that
    checks the workflow name against an immutable.
  · A lien exists that no one can alter. The registry has no owner, no pause and no proxy.

Not established:

  · Attestation is verified by the DON before the execution completes; nothing in this repository
    reads that verification.
  · The advance is committed, not paid. `disburse` is a separate permissionless call and the pool
    still holds 16,000,000 base units.
  · The collision check has still never fired against a real lien — there was nothing to collide
    with until this moment. That is now possible for the first time.
  · Release and default have never run on chain.
