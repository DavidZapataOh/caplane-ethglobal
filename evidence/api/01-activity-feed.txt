--- the four inherited events, which a naive watcher loses --------------------

`Transfer` 2 and `Deposit` 2 are ERC4626's, emitted by CaplanePool and declared in none of its
source files. Four of seventeen — a quarter of the feed. The watcher is built from signatures, not
from contracts/src, for exactly that reason; and the generated ABI would not have helped, since it
carries the registry and the inbox and neither the pool nor the escrow.

--- what is measured here and what is not ------------------------------------

Measured: the feed equals the chain, three ways, and it names the rejection's reason from the frozen
code table. The index holds no store — this run rebuilt all seventeen events from the deployment
block in eight pages, which is what a restart does.

NOT measured here, because it needs the service running on the platform:

  * the client-observed p95, which is why `services.api.p95Ms` is still null rather than a number
    with nothing behind it. See 00-latency.txt.
  * the outage run — api, mcp and the harness stopped, and the registry still answering. That
    belongs to the rehearsal, which owns the window: the same process also carries debtor
    confirmation, so the outage costs two things and must not land mid-confirmation.
