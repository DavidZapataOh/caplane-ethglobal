--- and the part a status code cannot tell you --------------------------------

DELIVERED: confirmed by the recipient, who found the message. That confirmation is separate
from the 200 on purpose. A 200 means the provider accepted the message for sending; it says
nothing about whether it reached anyone.

PLACEMENT: it landed in the spam folder, not the inbox. Recorded because it is the honest
result and because it matters to the layer that depends on this transport: a debtor who never
sees the message never confirms.

--- authentication is complete, so placement is reputation, not configuration --

  resend._domainkey.caplane.xyz   DKIM key published
  send.caplane.xyz                SPF for the return-path the provider actually uses
  _dmarc.caplane.xyz              v=DMARC1; p=none;

Nothing is missing. The domain simply has no sending history: this was the first message it
had ever sent, plain text, no links, to a major consumer provider. No DNS record fixes that.

What is being done about it: the recipients that matter are known to us, so they mark the
first message as legitimate and reply to it, which is the strongest positive signal available.
What cannot be done in the time available is cold deliverability to arbitrary third parties.
That is a limitation of the demonstration, not of the mechanism, and it is declared as one.

--- the credential is send-only -----------------------------------------------

$ GET https://api.resend.com/emails/<id>
  401 {"name":"restricted_api_key","message":"This API key is restricted to only send emails"}

Deliberate, and the reasoning survives a correction to the destination.

⚠️ This said the credential is "destined for the vault and therefore for the enclave". That was
wrong by architecture, not by plan: the enclave does not operate this channel. It would spend the
fifth HTTP call, and — the load-bearing half — it has no way to know which address to write to,
because the invoice response carries the contact's id and name and no email. The channel runs
outside, on the platform, which is where this credential belongs.

What holds either way is that it should be send-only: whichever side carries it should not be able
to read a mail history. The cost is that delivery state cannot be read back programmatically, which
is why the delivery line above is a human confirmation, and why the service says `accepted` and
never `delivered`.
